# Cross-judge: Kyoot cleanup designs A and B

## Recommendation

Use **A as the base** for the AI turn/replay model and for the explicit effect-contract direction. Graft from B the requirement that successful model completions, approval decisions, and tool receipts become durable within the in-memory turn record **before any later fallible notification or request**, plus B's tracked Registry cancellation settlement. Do not adopt B's full FIFO queue, `Turn`/`TurnProgram`/`Conversation` vocabulary, public abandonment protocol, or `running`-call join behavior as the initial cleanup. A's single conversation owner and fail-fast contention are easier to reason about and maintain.

A needs one important lifecycle fix before it is implementable: if a turn fails permanently and retains the conversation slot, the conversation is wedged. Either include a small explicit `discard`/`abandon` operation (must reject while running, preserve the partial audit state, release ownership, and prevent the partial assistant/tool protocol from being sent as an ordinary transcript), or state and enforce that callers must replace the AI instance. B correctly surfaces this problem with abandonment, but its larger protocol is unnecessary if the initial product accepts replacement or a narrow discard.

## Why A wins, with specific grafts

A has a compact ownership model: the turn created outside a retried generator owns its input, cursor, completion, and receipts; AI owns one active turn; a retry resumes that same record. A different call creates a different request even if its text matches. That identity rule is necessary: text matching is not a safe deduplication key. The active-turn guard also makes simultaneous calls deterministic without maintaining a pending-turn queue.

Graft B's explicit `approval` step into the turn cursor. `needsApproval` currently performs approval inside the tool program, before the tool's action. Treat approval decision and action as distinct outcomes so a retry after approval cannot prompt again or mistake approval for successful execution. Graft B's rule that a model completion is stored before interpreting tool calls, and that a tool receipt is committed before `Events.emit`; A says this in substance and should retain it as an invariant. Typed tool failure may be serialized as the existing tool error result. Defect or interruption after action start is an unknown external outcome and retry must stop with an explicit unknown-outcome result unless a tool later opts into replay safety.

For conversation state, choose one of two small contracts and make it explicit: hold the active turn across retriable failure and provide `discard`, or require creating a fresh AI after an unresolvable failed turn. Do not release ownership automatically and then let the old turn retry against a newer transcript. If partial turns are visible through `messages`, expose a snapshot and define whether it includes uncommitted pending turns. B's snapshot includes an open partial transcript; A's proposal to publish only completed messages avoids feeding an orphan assistant tool-call record into the next model request. Either behavior can work only with an explicit recovery boundary.

## Effect contracts and escape hatches

A's invariant answer witness is the stronger design sketch. `answer: (value: A) => A` makes the type parameter invariant under strict function checking, while the row stores both payload and answer. Preserve `V` (the requirement row value used by Env/Var) separately from actual performed payload `P`. `Payload` must retain `undefined`; optionality should be represented at the row boundary instead of stripped with `Exclude` or hidden with `Required`.

Neither design makes string keys nominal. Equal string keys are still one runtime dispatch family, so two declarations with the same key and equal contract must intentionally interoperate; same key with mismatched answer contract must fail at the checked API. This is a type-level guard, not proof that runtime declarations are distinct. Unique runtime tokens would require changing operation construction, dispatch, handwritten rows, and wrappers and are a larger migration.

Both designs understate the remaining public escape route. `packages/kyoot/src/index.ts` exports `op` and `makeHandler`; `makeHandler` accepts raw keys and currently types resume as `any`. `packages/ai/src/mode.ts` uses this route. A's preferred direction—make the trusted raw primitive private and migrate checked callers—is the sounder destination, but is not minimal unless the wrappers can be moved into core or given an explicit unsafe/internal boundary. B's explicitly named unsafe raw primitive is a more honest bridge. Do not describe A11 as fully sound while callers can combine public raw-key operations/handlers with arbitrary resume answers. Tests should include `undefined` through the checked effect and raw handler boundary, same-key mismatched answers, and a raw-operation example documenting the trust boundary.

## Registry cancellation

Prefer B's tracked cleanup ownership. The current `Registry.use` allocates its entry when the Kyoot is constructed, appends it when the promise executes, then waits for refresh before returning the only removal handle. `Async.fromPromise` observes abort, but the caller Fiber can reject before the external async callback's cleanup has settled. Therefore an abort listener alone is not enough, and an internal Kyoot handler is sufficient only if a registry-owned cleanup promise remains visible to `settled()`/`dispose()` until it finishes. Allocate an entry per execution; mark it unregistered before transitions; make desired activation depend on registration plus dependency satisfaction; and have remove/dispose/cancel share an idempotent transition path. A may still supply the single transition/removal abstraction; B supplies the clearest settled-ownership guarantee.

## Design red flags checked

- **Split ownership:** A assigns progress to a private turn record and conversation ownership to AI. Avoid also storing independent generation progress in `AI` and `generate`. B's `Conversation` plus public Turn lifecycle risks exposing coordination state, but it can remain private.
- **Temporal decomposition / pass-throughs:** Keep `generate` as the driver over the turn record. Do not make `Turn`, `TurnProgram`, and `Conversation` layers that simply forward to each other.
- **Information leakage:** Keep provider IDs, cursor representation, approval state, and queue mechanics private. Avoid making storage/journal schemas public for an in-memory cleanup.
- **Two ways to do one task:** Direct `generate` and AI `ask` must share one turn-record mechanism; do not leave `generate` as a retry-unsafe second path.
- **Unknown outcome:** Neither in-memory cursor protects the gap after an external tool acts but before its result is recorded (process crash, or unobservable defect timing). Call this `unknown`; do not promise exactly-once external actions.

## Source basis

The source matches both proposals' core diagnosis: `Retry.run` reruns a Kyoot value; `generate` keeps `added` and `round` inside the generator; `AI.make` mutates the prompt before generation and appends `added` only on return. Runtime dispatch finds handlers by string equality. The row's `Payload` currently excludes `undefined`; `makeHandler` uses `Hooks<P, any, ...>`. Fork snapshots retain handler-state references and `inherit` installs those references as initial state, while Resource explicitly uses `fork: "scope"`. Registry's promise callback ignores the provided abort signal and returns its handle only after refresh.
